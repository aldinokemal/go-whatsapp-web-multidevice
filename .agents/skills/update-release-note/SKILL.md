# Update release notes

Resolve the requested repository and release tag; clarify only if the target is
ambiguous. Use the same explicit repository and tag for every read and write.
Read its current body and the previous release with
`gh release view <tag> --repo <owner/repo> --json name,body,url`; release-list
JSON does not include `body`. Inspect commits/PRs between the relevant tags to
support each change listed, while retaining existing accurate content and links.

## Default GOWA format

For `aldinokemal/go-whatsapp-web-multidevice`, use the English format established
by [v9.7.0](https://github.com/aldinokemal/go-whatsapp-web-multidevice/releases/tag/v9.7.0)
and adopted for v9.8.0 and v9.9.0 automatically. The user does not need to request
this format again. A minimal autogenerated `## Changelog` body is incomplete
source content, not the formatting template. The structure below is self-contained;
read v9.7.0 when additional presentation detail is needed.

Use this order and these heading styles:

1. `## What's New in <tag>`.
2. A short emoji-led, bold theme line, followed by a paragraph summarizing the
   release's user-visible changes.
3. `---`, then `## ✨ Features`. Group related features under descriptive `###`
   headings with supporting PR links and concise behavior bullets.
4. `---`, then `## 🐛 Bug Fixes`. Use the same subsection and bullet style to
   explain the corrected behavior and its impact.
5. `---`, then `## 🔧 Technical Improvements`. Summarize dependencies,
   infrastructure, documentation, and maintenance changes with evidence links.
6. `## Upgrade Notes` when there are compatibility changes, changed defaults,
   migration steps, or relevant limitations. State the affected settings and
   required operator action. Omit this section when there is nothing to report.
7. `---`, then `## What's Changed`. List the commits/PRs in the release interval
   as `* <title> ([#<number>](<PR URL>)) by @<author>`. For changes without a PR,
   use a linked short commit SHA in place of the PR link.
8. `## Contributors`. List verified human contributors as linked GitHub handles,
   including credited co-authors when their identities are confirmed.
9. End with `**Full Changelog**: <repository URL>/compare/<previous tag>...<tag>`.

Omit empty feature, fix, or technical sections rather than inventing entries.
Preserve accurate information and links while moving them into this structure;
replace raw hash-only autogenerated notes with the linked What's Changed format.
Keep claims within the evidence, including optional fields, experimental features,
and retry or delivery limitations. Do not present an acknowledgment as confirmed
delivery or promise exactly-once behavior without evidence.

When updating several releases, derive each release's content from its own
previous-tag interval and verify each stored body separately. For other
repositories, follow their established release-note format unless directed otherwise.
An explicit user-requested format overrides this default.

## Publish and verify

Write the complete intended Markdown to a temporary file. If the current body already
matches, return its URL without rewriting it. For a requested update, use
`gh release edit <tag> --repo <owner/repo> --notes-file <path>` and read the release
back to compare the stored body with the intended Markdown before reporting success.
A request for a draft or review ends with the proposed notes; it does not authorize
publishing them.
Creating a release or changing version/tag metadata requires a separate request.
